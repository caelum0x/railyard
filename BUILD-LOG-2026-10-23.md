### Item 12 -- Watch's missing scheduled check-runner (`stacks/gatus-customers`)

Closed the real gap, not a rename: `apps/console/README.md` already documented
`WATCH_AGENT_TOKEN` as "Bearer token of the box 1 checks agent
(`stacks/gatus-customers/agent.sh`)" and `lib/watch/types.ts` already said
"the customer checks run on a Gatus instance of their own on box 1 ... an
agent next to it pulls the list of checks from this console and pushes each
result back" -- but that file, and everything around it, did not exist. The
console side (`lib/watch/service.ts`'s `agentChecks`/`recordResults`,
`app/api/v1/watch/agent/*`) was built in an earlier round and had nothing on
the other end to call it.

- `stacks/gatus-customers/docker-compose.yml` + `config/config.yaml` --
  [Gatus](https://github.com/TwiN/gatus) (MIT, `ghcr.io/twin/gatus:stable`),
  bound to `127.0.0.1:8083` only, sqlite storage, one permanent internal
  self-check endpoint (see "real bug" below for why), customer endpoints
  supplied entirely by `config/endpoints.generated.yaml` (GATUS_CONFIG_PATH
  directory-merge).
- `stacks/gatus-customers/agent.sh` -- the actual missing bridge, one pass:
  `GET` the console's `/api/v1/watch/agent/checks` (bearer
  `WATCH_AGENT_TOKEN`) -> rewrite `endpoints.generated.yaml` (restart gatus
  only if the check list actually changed) -> `GET` gatus's own
  `/api/v1/endpoints/statuses` -> `POST` the translated results batch to
  `/api/v1/watch/agent/results`. Keeps no state of its own: the console
  already dedupes by `last_checked_at`, so resending results it has is
  always safe. `./agent.sh once` for one pass (install/manual), bare
  `./agent.sh` loops forever on `WATCH_POLL_INTERVAL_S` (default 30s).
- `stacks/gatus-customers/agent.env.sample`, `systemd/watch-agent.service`,
  `install.sh` -- same box-1 install shape as
  `tools/reconcile-relay-rago` (`sudo ./install.sh` / `run` / `status`).
- `stacks/gatus-customers/README.md` -- the flip sequence (mint a token with
  the console, run `install.sh`, confirm one real pushed result, then set
  `RAILYARD_WATCH_LIVE=1`) and why Gatus over a hand-rolled prober
  (research-and-reuse: a maintained probe engine with its own HTTP client,
  retries and storage, not something worth re-implementing for this).

Two real bugs found and fixed by actually running it, not by reading it:

1. Gatus refuses to start with zero endpoints in its merged config -- true
   on a fresh box, or any time every customer check is paused. Fixed by
   giving `config.yaml` one permanent loopback self-check (`gatus-self-check`,
   group `railyard-internal`) so Gatus always has >=1 valid endpoint
   regardless of the customer list; `agent.sh` filters that group out before
   it ever reaches the console's results endpoint.
2. The generated config's header comment included a timestamp, so the file
   never byte-matched the previous pass even when the check list had not
   changed -- `agent.sh` was restarting the gatus container on *every single
   pass*. Fixed by dropping the timestamp; confirmed fixed (second pass logs
   only a push, no restart).
