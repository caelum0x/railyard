# Railyard — prioritized feature backlog (2026-10-23)

Built from a fresh read of the live code (not the pitch) plus
`STRATEGY-2026-10-23.md` (competitive positioning, growth moves) and
`docs/CONSUMERS.md` (per-product wiring gaps). No `ARCHITECTURE-2026-10-23.md`
exists in this repo at time of writing — the canonical architecture doc is
`docs/RAILYARD_ENTERPRISE_ARCHITECTURE.md`, referenced inline below instead
of duplicated.

Ground truth restated from STRATEGY.md: one real self-serve product
(Insights), one unified console built-but-undeployed (`apps/console`,
blocked on an owner-only Scribase project provisioning step — confirmed live
2026-10-21/22, see `apps/console/NOTES.md`), and five-to-seven backend rails
(Relay, Rago, Switchyard/toolgate, Vend, Mint, Rithub) with no self-serve
signup path at all. The backlog below is ordered so the top items are the
ones that convert existing traffic/usage into signups or revenue fastest,
and the owner-blocked console deploy itself is called out once (item 1) with
every non-owner-blocked thing done in its shadow, rather than repeated as a
blocker under every other item.

## 1. Console cross-sell: prefilled signup bridge from Insights → Console
**Why #1:** STRATEGY.md names this the single highest-leverage growth move —
it is the only lever that converts the one proven self-serve funnel
(Insights, live at `insights.ereboslab.com`) into Console signups, and it
costs no new backend, only a bridge between two already-built flows.
- Add a dismissible banner to the Insights dashboard
  (`apps/insights-edge` dashboard view) once a site has recorded ≥1 real
  event: "See errors, flags and model spend for this site too — open your
  Railyard account", linking to
  `https://railyard.ereboslab.com/auth/start?email=<encoded>&src=insights`.
- In `apps/console/app/auth/start`, read `?email=` and `?src=` query params
  and pre-fill the email-code form (`apps/console/lib/email-signin.ts`) so
  the user only confirms, never retypes an address; store `src` on the
  session row created in `apps/console/lib/session.ts` for attribution.
- Ship this on `main` now even though the Worker itself is not deployable
  yet (owner-only Scribase step, see `apps/console/NOTES.md`) — it is ready
  to go live the moment that one step clears, instead of being designed
  after the fact.

## 2. "Relay vs. OpenRouter: $0 markup vs. 5.5-8%" comparison page
**Why #2:** STRATEGY.md calls this "the single clearest, most defensible
price-axis claim in the whole portfolio" — it is a page, not a pitch, and it
targets search queries ("OpenRouter alternative no markup") that already
have third-party demand.
- New public page, e.g. `apps/console/app/(marketing)/compare/relay-vs-openrouter/page.tsx`
  (or a static page under the main railyard marketing site if one is
  separate from `apps/console`): a real numbers table (spend tiers
  $1k/$10k/$100k/mo → OpenRouter fee in dollars vs. Relay's $0 markup), the
  success-only-billing mechanism explained in one paragraph, and a CTA into
  the Console signup from item 1.
- Submit the finished URL to the exact channels STRATEGY.md's own research
  surfaced organically ranking for this (awesome-llm-gateway GitHub lists,
  r/LocalLLaMA, HN Show-HN) — a distribution task, not a build task, but
  track it here so it isn't dropped once the page exists.

## 3. Faultline folded into Console's usage meter (not a separate bill)
**Why #3:** STRATEGY.md's gap analysis: Faultline today is "GlitchTip with a
new logo" and has no differentiation reason to exist; Rago already meters
`insights_events` the same way, so this is the cheapest real differentiation
available.
- Add a `error_events` metric alongside the existing `insights_events` metric
  in `apps/rago` seeds/plan config, and a GlitchTip→Rago webhook bridge
  (new small service, same shape as `apps/gitea/integrations/railyard/webhook-bridge/bridge.mjs`)
  that POSTs an event to Rago per received GlitchTip error webhook.
- Add a "Faultline" tab to `apps/console/app/(app)` (next to the existing
  `insights`, `flags`, `watch` tabs) that reads error counts for the org's
  sites/projects and shows them against the same plan cap as Insights.
- Update the plan copy in `apps/console/lib/plans.ts`/`ladder.ts` so error
  events count toward the existing bundle cap instead of being unmentioned.

## 4. Public landing + self-serve signup page for Rithub (git forge) — DONE 2026-10-24
**Why #4:** Rithub is live (`git.ereboslab.com`, HTTP 200) with zero
discovery/signup surface — pure wasted existing infrastructure, the cheapest
kind of growth to capture.
- Built: `apps/console/app/rithub/page.tsx` (public pitch page) +
  `apps/console/app/api/v1/rithub/provision/route.ts` (session-authed) +
  `apps/console/lib/gitea.ts` (admin API client, `sudo=` impersonation) +
  `apps/console/db/migrations/0014_org_gitea.sql`. See
  `BUILD-LOG-2026-10-23.md`'s "Round 2" for the full verification (a real
  `gitea/gitea:1.23` container, end to end).
- Gated behind the same Console sign-in from item 1, via item 5's OIDC
  prerequisite (closed in round 1) — Rithub access is reached by signing
  into Console, not a separate native-Gitea-account flow.
- Owner-only step: set `GITEA_API_URL`/`GITEA_ADMIN_TOKEN` in production
  (mint a site-admin token once on `git.ereboslab.com`); the route answers
  503 with that exact instruction until then.

## 5. Rithub OIDC/SSO into Console (close `TODO(railyard-sso)`)
**Why #5:** STRATEGY.md: "ship that before claiming 'one bill, one sign-in'
anywhere in marketing copy, or the claim is false on day one" — this is a
prerequisite for item 4's CTA to actually be one sign-in rather than two.
- Add an OIDC discovery endpoint to `apps/console`
  (`/.well-known/openid-configuration`, `/oauth/authorize`, `/oauth/token`,
  `/oauth/userinfo`) backed by the existing session/JWT machinery in
  `apps/console/lib/session.ts` and `apps/console/lib/tokens.ts`.
- Configure Gitea's `OAUTH2_PROVIDER` block in `apps/gitea/docker-compose.yml`
  (the inline `TODO(railyard-sso)` marks exactly this spot) to point at the
  new discovery endpoint, so a Console session logs a user straight into
  Rithub with no second credential.

## 6. Switchyard (toolgate) self-serve signup — replace the admin-curl bootstrap
**Why #6:** STRATEGY.md and `apps/toolgate/README.md` both confirm onboarding
today is an admin-token `curl` call; this is the only rail in the repo with
real usage-ready infra (24 capabilities, 27 tools, MCP server, `sy` CLI) and
zero way for an outside developer to get a key without asking the owner.
- New `POST /v1/auth/signup` endpoint in `apps/toolgate` (mirror the pattern
  already shipped in `apps/vend`'s `VEND_SIGNUP_ENABLED` flow: email +
  workspace name in, `sk-t0-` key + session out, rate-limited per email).
  Reuse Relay's own `sk-t0-` key format since Switchyard already shares
  Relay's keys per the README.
- A minimal `/console` page in `apps/toolgate` (or a tab inside
  `apps/console`) listing the 24-capability/27-tool catalog with live
  pricing (`GET /v1/tools` already exists server-side per the README —
  this just needs a web page, not a new API) and a "Create key" button
  that calls the new signup endpoint.

## 7. Flip Vend's self-serve signup live + give it a landing page
**Why #7:** Unlike Switchyard, Vend already has a working signup endpoint
(`POST /v1/auth/signup`) and a full `/console` (Apps/Earnings/Team/Account)
gated only by the `VEND_SIGNUP_ENABLED` operator flag — this is the cheapest
item in the whole backlog, pure config + a landing page, not new code.
- Flip `VEND_SIGNUP_ENABLED=true` in Vend's deploy env (zero cost — no new
  paid account, just an env var) and confirm the live `/v1/auth/signup`
  default-terms response via `GET /v1/auth/signup`.
- Write the landing page the existing flow has never had: "resell LLM
  access under your own brand" pitch (Vend's actual value prop per its
  README: wallets, per-model prices, revenue splits), with a form that
  POSTs straight to the already-built signup endpoint.

## 8. Rally (vcpeer.com) — close the two named Railyard-wiring gaps
**Why #8:** `docs/CONSUMERS.md` names these as open gaps for a product
already fully wired to Railyard everywhere else — finishing them converts
already-paying Rally usage into Railyard-metered usage without any new
product surface, i.e. pure revenue capture on existing traffic.
- **Abacus caps on `chat-fetch`:** extend `lib/railyard/abacus.ts`'s cap
  enforcement to `lib/railyard/chat-fetch.ts` (today caps apply only to
  `railyard-llm`/`gtm-llm`), and add a per-project `ABACUS_AGENT_ID` mapping
  table so caps are per-customer, not per-deployment — the exact gap named
  in `docs/CONSUMERS.md` item 6.
- **Rally subscription plans through Rago:** wire VC-viewer and Rally-seat
  plan usage into Rago metering events (`lib/autogtm/rago-billing.ts`
  pattern, new metric e.g. `rally_seat_active_month`) while Creem remains
  the payment processor — `docs/CONSUMERS.md` item 4's explicit target
  wiring.

## 9. Embeddings path through Relay for Rally
**Why #9:** `docs/CONSUMERS.md` gap 2 — Anthropic SDK and Voyage-rerank
embedding calls bypass Relay entirely today, meaning that spend is both
unmetered (no Rago event) and uncapped (no Abacus hold) even though every
other Rally LLM call site already goes through Relay.
- Add an OpenAI-compatible `/v1/embeddings` route to `apps/relay` that maps
  to the TensorZero embedding backends already vendored in the fork, priced
  in the same per-model catalog Relay uses for chat.
  Switch `lib/embeddings/adapter.ts` in Rally to call this route the same
  way `lib/railyard/chat-fetch.ts` wraps chat calls, env-gated so the direct
  Voyage/Anthropic path remains the fallback.

## 10. Menivor per-render media-gateway metering
**Why #10:** `docs/CONSUMERS.md`: Menivor's `media_gateway.py::_settle_job`
jobs are "not metered per render" even though wallet holds/captures already
flow through Mint for the rest of Menivor — this is unbilled usage on a
product that already charges for renders everywhere else.
- Add a `railyard/metering.py`-style call (mirroring the existing
  `app/integrations/railyard/metering.py` hook already used by
  `wallet_bridge._meter_settlement`) into `media_gateway.py::_settle_job`
  so every gateway-dispatched render emits the same `reel_ai_credits`/
  per-render Rago event the rest of Menivor's render path already does.

## 11. Mint account self-provisioning (close the "no UI" gap)
**Why #11:** `docs/CONSUMERS.md` gap 5 — Rally's `mint-settlement.ts` needs
Mint accounts "provisioned per project out of band," with "no UI to create
them yet," which blocks every other item above that assumes a project
already has a Mint account.
- Add a `POST /v1/accounts` self-serve endpoint (if not already present —
  `apps/mint` has the core ledger primitives per the README's 10-crate
  shape) plus a small admin page under `apps/console/app/(app)/apps` to
  create/view a project's Mint account id and balance inline with the rest
  of the Apps tab, instead of a manual out-of-band step.

## 12. Watch (uptime) — finish the gated feature, flip it live
**Why #12:** Watch already has real code (`apps/console/app/(app)/watch`,
`apps/console/lib/watch/service.ts`) gated behind `RAILYARD_WATCH_LIVE` and a
32+ char `WATCH_AGENT_TOKEN` — this is a built feature sitting behind a flag,
cheaper to finish than anything net-new, and PostHog/UptimeRobot comparisons
in STRATEGY.md make clear uptime is a real wedge once live.
- Audit `apps/console/lib/watch/service.ts`'s `listWithState` for the actual
  check-runner gap (the flag name implies a separate agent process is
  expected to exist); build the missing scheduled-check runner (cron-style
  HTTP/TCP probe worker, same shape as the other Rust `*-server` binaries in
  this repo) if it doesn't already run anywhere, then set
  `RAILYARD_WATCH_LIVE=1` and a real `WATCH_AGENT_TOKEN` in deploy env.
- Add a public status page per monitored app at
  `apps/console/app/status/[app]` (route already scaffolded — confirm it
  renders real check data once the runner is live, not a placeholder).

## 13. Switchyard catalog browser + `llms.txt` publish
**Why #13:** Switchyard's `/mcp` and `llms.txt` surfaces exist server-side
per the README, but there's no human-browsable catalog page — agent
developers evaluating Switchyard today have to read raw JSON from
`/v1/tools/*` instead of a page they can scan and link to.
- Build a simple `/catalog` page in `apps/toolgate` (or console tab) that
  renders the 24-capability/27-tool manifest with live pricing from
  `catalog/`, sortable by capability, with copy-paste `curl`/`sy` snippets
  per tool — directly reusable by the signup flow in item 6.

## 14. Console setup-wizard to minimize the owner-only deploy step
**Why #14:** The console deploy is blocked on exactly one owner action
(provisioning a `railyard-console` Scribase project, per
`apps/console/NOTES.md`'s 2026-10-22 entry) — everything else (toolchain,
secrets, `wrangler deploy`) is already proven to work from this machine.
Rather than wait on that step, reduce it to the single smallest possible
click.
- Build a one-page `DEPLOY-CHECKLIST.md` + a `scripts/finish-console-deploy.sh`
  that: checks `SCRIBASE_URL` against the control-plane host guard in
  `lib/config.ts`, and once the owner pastes the new project's gateway host
  into one env var, runs `cf:build` + `wrangler deploy` + the item 1-13
  smoke checks automatically — so the owner's total manual work is "create
  one Scribase project, paste one URL," not a multi-step runbook.
- Separately: check whether an existing, already-provisioned Scribase
  project (any other product's) could serve as `railyard-console`'s
  backend short-term, the same way Dodo's "one business, many Brands"
  pattern let CalDesk reuse Bidstage's live key — if viable, this removes
  the owner-only step entirely instead of just shrinking it.

## 15. Insights multi-site billing fix (per-site pricing penalty)
**Why #15 (lowest ranked, still concrete):** STRATEGY.md's competitor table
flags that Plausible-style per-site pricing "penalizes multi-property teams"
— Insights should differentiate on exactly this axis since it already has
the only live self-serve funnel in the repo.
- Add an org-level (not site-level) event pool to `apps/insights-edge`'s
  plan logic so a team running 5 small sites shares one 10,000-event/month
  free pool and one paid tier, instead of hitting 5 separate site caps —
  a real pricing-model change, surfaced on the existing dashboard with a
  "pooled across N sites" line item.

## Addendum: per-app pages / APIs / features spec (2026-10-23)

Terse technical spec, one block per `apps/*` directory plus railyard core
(CLI + Rithub/Gitea + CI runner). Internal build doc — not restating code
that's self-evident from the route table, only the shape an implementer
needs. "Live" = curl-verified 200 on 2026-10-23; everything else is coded,
not confirmed serving real traffic.

### Core: CLI (`packages/cli`)
- No pages (terminal tool). Commands: `login`, `deploy`, `rollback`,
  `deploys`, `logs`, `link`, `ci`, `domains` — each a thin HTTP client
  against `apps/console`'s `/api/v1/*`.
- Auth: device-code flow (`POST /api/v1/device/code` → poll
  `/api/v1/device/token`), token cached in `~/.railyard/credentials.json`.
- Remaining: none blocking; `railyard logs` (added 2026-10-22) was
  load-tested against a long-running tail 2026-10-24 (see
  `BUILD-LOG-2026-10-23.md` "Round 4") -- found and fixed a real unbounded-
  memory bug in `run()`'s output capture, now covered by tests.

### Core: Rithub/Gitea + CI runner (`apps/gitea`, live `git.ereboslab.com`)
- Pages: stock Gitea 1.23 UI (repos/issues/PRs/Actions/Packages/Wiki) +
  Railyard branding overlay (`apps/gitea/custom/`).
- APIs: Gitea REST `api/v1/*` + Actions API, consumed by the registered
  `act_runner` (gitea/act_runner:0.6.1).
- Features: Postgres 17 via docker-compose, Rago/Mint billing bridge
  (`integrations/railyard/webhook-bridge/bridge.mjs`), HTTPS+SSH push, LFS,
  npm registry. CI proof: push → queued → running → success verified
  2026-10-20.
- Remaining: none blocking — Console is now a real OIDC provider for Rithub
  (backlog item 5) and `apps/console/app/rithub` self-serve-provisions an
  org + first repo per Console session (backlog item 4), both closed
  2026-10-24 (see `BUILD-LOG-2026-10-23.md` "Round 2").
- `apps/rithub` (own forge, 27.8k LOC) and `apps/rithub-forge` (Forgejo
  submodule) are superseded, kept per no-delete rule, not deployed —
  do not plan new work against either unless re-adopting one as primary.

### apps/mint (ledger/billing core)
- Page: `GET /admin` (`assets/admin.html`) — operator console only.
- API: ~60 routes under `/v1/*` (accounts, holds, transfers, allowances,
  streams, checkouts, payouts, providers, keys, AITP-402, mint marketplace
  under `/mint/v1/sellers/:seller/*`, webhooks for Dodo/Stripe Connect),
  `/healthz`, `/readyz`. Auth: operator Bearer token on `/v1/admin/*`-style
  calls (verify per-route in `mint-server/src/routes`), signed webhooks
  verified by provider secret.
- Features: double-entry ledger, Ed25519 hash-linked receipts, success-only
  billing, hold→capture/release, AITP-402, multi-provider on-ramp, KYC-tiered
  redeem, payout reconciliation, Google Play RTDN (added 2026-10-22).
- Remaining: no founder-facing self-serve page (operator-only); wiring into
  Rally/Menivor/Scribase is env-gated and off per `docs/CONSUMERS.md`.

### apps/relay (model gateway, TensorZero fork)
- Pages: forked TensorZero React Router SPA — api-keys, autopilot,
  billing/{budgets,events,keys,settlements}, config, datapoints, datasets,
  evaluations, observability/{episodes,functions,inferences}, models,
  health, index.
- API: `/health`, `/status`, `/openai/v1/*`, `/inference` (vendored), plus
  owned additions `/v1/relay/catalog`, `/v1/relay/quotes`,
  `/v1/models/list`, `/api/v1/events`, `/relay/traces`, `/openai/files`.
  Auth: per-API-key Bearer, budget-checked.
- Features: per-key spend budgets, operator-editable price catalog w/
  OpenRouter list-price refresh, fallback routing/circuit-breaking/latency
  hedging.
- Remaining: comparison page vs. OpenRouter (see backlog item 2) not built;
  275 TODO/FIXME markers exist but the large majority are vendored
  TensorZero engine code, not owned-overlay gaps (not individually
  triaged — out of scope for a terse spec).

### apps/rago (billing/metering, Lago rewrite)
- Pages: `GET /admin` (`assets/admin.html`), `GET /portal/:token`
  (customer self-serve portal).
- API: 234 distinct routes — customers, subscriptions, plans(+charges),
  invoices(+pdf/xml/finalize/void/refund), credit_notes, wallets, coupons,
  billable_metrics, events(+batch/estimate_fees), add_ons, taxes,
  rate_cards, features, orders/quotes, payments, data_exports,
  dunning_campaigns, activity/api/security logs, webhook_endpoints,
  integrations(oauth/CRM/accounting sync), analytics/*, GraphQL dashboard
  API, `auth/sso/{authorize,callback}`, `portal/:token/*`,
  `webhooks/{stripe,creem,dodo,adyen,gocardless,iyzico}/:organization_id`,
  `/health`, `/metrics`. Auth: API key (server), session (portal/GraphQL),
  provider webhook signature.
- Features: exact decimal money math end-to-end, 6 payment-provider
  webhooks, durable background worker.
- Remaining: 13 files with TODO/stub markers, not individually triaged.
